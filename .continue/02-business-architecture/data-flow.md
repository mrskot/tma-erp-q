# ПОТОКИ ДАННЫХ TMA-ERP-Q

## Общий обзор архитектуры потоков данных
Система TMA-ERP-Q построена вокруг цикла управления качеством с акцентом на доказательную базу и аудит. Все потоки данных следуют принципам из раздела 5 `concepts.md` (Immutable Audit Trail, Resilient Integration и др.).

## Основные потоки данных

### 1. Поток создания и обработки заявки на приёмку (Application Flow)
**Бизнес-контекст:** Мастер создает заявку на контроль качества для конкретного изделия/партии.

**Участники:**
- Мастер участка (Master)
- Система TMA-ERP-Q
- Контролёр ОТК (OTK Inspector)
- Очередь заданий (для внешних интеграций)

**Шаги потока:**
1. **Создание заявки:**
   - Мастер через Telegram или веб-интерфейс создает заявку
   - Указывает: Участок (Lot), Тип изделия (Product), желаемый срок приёмки
   - Загружает фото МКИ (если политика обязательности фото включена)
   - Система валидирует данные, создает запись в таблице `applications`
   - Статус: `новая`

2. **Назначение контролёру:**
   - Система определяет доступного контролёра (по загрузке или ротации)
   - Заявка назначается контролёру
   - Статус меняется на `назначена`
   - Запись в `activity_log`: "Заявка назначена контролёру [ID]"
   - Если интеграция с Bitrix24 включена: создается задача в очереди синхронизации

3. **Проведение контроля:**
   - Контролёр получает чек-лист для типа изделия
   - Проводит проверку по пунктам
   - Фиксирует результаты (passed/failed для каждого пункта)
   - Загружает фото доказательств (дефектов)
   - Статус меняется на `в работе`
   - Запись в `activity_log`: "Начат контроль"

4. **Завершение контроля:**
   - Если все пункты пройдены: статус `принята`
   - Если найдены дефекты: статус `отклонена`, создаются Несоответствия
   - Система автоматически вычисляет итоговый статус на основе связанных несоответствий
   - Запись в `activity_log`: "Контроль завершен, статус: [статус]"

**Ключевые данные:**
- `applications`: основная информация о заявке
- `application_items`: результаты проверки по пунктам чек-листа
- `application_photos`: фото МКИ и доказательств
- `activity_log`: полная история изменений

### 2. Поток управления несоответствиями (Discrepancy Flow)
**Бизнес-контекст:** Обработка дефектов, найденных при контроле или зафиксированных автономно.

**Участники:**
- Контролёр ОТК (создает несоответствие)
- Система TMA-ERP-Q
- Ответственный (Мастер или Рабочий)
- Директор качества (для сложных случаев)
- Очередь заданий

**Шаги потока:**
1. **Создание несоответствия:**
   - Автоматически при отклонении заявки ИЛИ вручную любым сотрудником
   - Заполняются: описание, серьезность (minor/major/critical), фото дефекта
   - Система определяет ответственного по правилам (Мастер участка)
   - Создается запись в `discrepancies`
   - Статус: `открыто`

2. **Назначение ответственности:**
   - Автоматическое назначение по участку/правилу
   - Возможность ручного изменения контролёром или директором качества
   - Мастер может делегировать устранение Рабочему
   - Запись в `activity_log`: "Ответственный назначен: [ID]"

3. **Устранение несоответствия:**
   - Ответственный принимает меры по устранению
   - Загружает фото исправления (если требуется)
   - Отмечает выполнение
   - Статус меняется на `ожидает проверки`

4. **Проверка устранения:**
   - Контролёр проверяет устранение
   - Если устранено: статус `устранено`
   - Если не устранено: возврат на доработку
   - Запись в `activity_log`: "Проверка устранения, результат: [результат]"

5. **Сценарии закрытия (альтернативные):**
   - **Карточка разрешения (КР):** Формальное согласование отклонения
   - **Брак:** Окончательное списание
   - **Политическое закрытие:** Решение руководства
   - Каждый сценарий имеет свой workflow и утверждения

**Ключевые данные:**
- `discrepancies`: основная информация о несоответствии
- `discrepancy_photos`: фото дефектов и исправлений
- `discrepancy_resolutions`: информация по сценариям закрытия
- `activity_log`: полная история

### 3. Поток синхронизации с внешними системами (Integration Flow)
**Бизнес-контекст:** Обмен данными с Telegram и Bitrix24 через очереди для обеспечения отказоустойчивости.

**Участники:**
- Система TMA-ERP-Q
- Очередь заданий (`sync_queue`)
- Telegram Bot API
- Bitrix24 API (опционально)

**Шапы потока Telegram:**
1. **Исходящие уведомления:**
   - Событие в системе (новая заявка, изменение статуса и т.д.)
   - Создание задания в `sync_queue` с типом `telegram_notification`
   - Worker обрабатывает задание, отправляет сообщение через Bot API
   - При успехе: отметка `synced_at`
   - При ошибке: retry с экспоненциальной задержкой

2. **Входящие команды:**
   - Пользователь отправляет команду/сообщение в бота
   - Telegram Webhook → обработчик команд
   - Валидация пользователя (роль, права)
   - Выполнение действия (создание заявки и т.д.)
   - Ответ пользователю

**Шапы потока Bitrix24 (опционально):**
1. **Синхронизация сущностей:**
   - Создание/обновление заявки/несоответствия
   - Создание задания в `sync_queue` с типом `bitrix_sync`
   - Worker отправляет данные в Bitrix24 API
   - Сохранение `external_id` для последующих обновлений
   - Отдельная таблица `sync_status` для отслеживания состояния

2. **Двусторонняя синхронизация:**
   - Периодическая проверка изменений в Bitrix24
   - Импорт обновлений (статусы, комментарии)
   - Разрешение конфликтов (приоритет у TMA-ERP-Q)

### 4. Поток аудита и отчётности (Audit & Reporting Flow)
**Бизнес-контекст:** Сбор данных для аналитики, отчётности и неизменяемого аудита.

**Участники:**
- Система TMA-ERP-Q
- Таблицы аудита (`activity_log`, `system_logs`)
- Сервис отчётности
- Пользователи (для просмотра аналитики)

**Шапы потока:**
1. **Запись аудита:**
   - Любое значимое изменение в системе
   - Автоматическая запись в `activity_log`: кто, когда, что изменил, старые/новые значения
   - Маскирование чувствительных данных перед логированием

2. **Сбор метрик SLA:**
   - Фоновый процесс вычисляет метрики:
     - Время реакции ОТК (created_at → assigned_at)
     - Время проверки (assigned_at → final_status)
     - Процент соблюдения сроков (желаемый срок приёмки)
   - Сохранение в таблице `sla_metrics` для быстрого доступа

3. **Генерация отчётов:**
   - Пользователь запрашивает отчёт (горячие точки, эффективность и т.д.)
   - Система собирает данные из `activity_log`, `applications`, `discrepancies`
   - Агрегация по участкам, типам изделий, ответственным
   - Предоставление в UI с возможностью экспорта в CSV/Excel

4. **Мониторинг здоровья:**
   - Регулярные health checks к БД, Telegram API, Bitrix24
   - Запись результатов в `system_health`
   - Алёрты при деградации сервисов

## Диаграмма потоков данных (текстовое представление)

```
[Telegram User] → [Telegram Bot API] → [Webhook Handler] → [Business Logic]
       ↑                                      ↓
[Уведомления] ← [Notification Service] ← [Event Bus] ← [Database Changes]
       ↓
[Sync Queue] → [External APIs (Bitrix24)] → [Sync Status Tracking]

[Business Logic] → [Database] → [Activity Log]
       ↓               ↓
[Reporting Service] → [SLA Metrics] → [Analytics Dashboard]
```

## Принципы обработки данных

1. **Immutable Audit Trail:** Каждое изменение → запись в `activity_log` с полным контекстом
2. **Resilient Integration:** Все внешние вызовы → через очередь с retry механизмом
3. **State vs Timeline:** Приоритет истории (`activity_log`) над текущим состоянием
4. **Backend as Source of Truth:** Вся бизнес-логика на сервере, фронтенд только интерфейс
5. **Runtime Configuration:** Параметры системы в `system_config`, изменение без перезапуска

## Таблицы данных и их связи

```
applications
├── id (PK)
├── lot_id (FK → lots)
├── product_id (FK → products)
├── master_id (FK → users)
├── inspector_id (FK → users, nullable)
├── status (новая/назначена/в работе/принята/отклонена)
├── desired_deadline (желаемый срок)
└── ...

discrepancies
├── id (PK)
├── application_id (FK → applications, nullable)
├── responsible_id (FK → users)
├── status (открыто/ожидает/устранено/...)
├── closure_scenario (устранение/КР/брак/полит.)
└── ...

activity_log
├── id (PK)
├── entity_type (application/discrepancy/user)
├── entity_id
├── user_id (кто изменил)
├── action (created/updated/status_changed/...)
├── old_values (JSON)
├── new_values (JSON)
└── timestamp

sync_queue
├── id (PK)
├── entity_type
├── entity_id
├── action (create/update/delete)
├── external_system (telegram/bitrix24)
├── status (pending/processing/completed/failed)
├── retry_count
└── ...
```
